## Runtime ownership and safety invariants

- The host has one GPU. WHAM/GVHMR reconstruction, Qwen, and managed Clef must not overlap GPU ownership. Keep `GlobalGpuLock`/`gpu_stage_lock` and the shared-server quiesce protocol as the ownership boundary.
- The PowerShell supervisor owns the long-lived shared llama server and its workspace/session lease. Wave clients attach to that server; attached clients do not own or stop it. Exclusive reconstruction quiesces it; the supervisor restarts it only when the staged-wave checkpoint is safe.
- Warm WHAM/GVHMR workers are persistent run-scoped services, started lazily and stopped before VLM work when required. Do not make both GPU models resident to hide restart time.
- Clef's managed SystemOne process is started and stopped inside its exclusive GPU owner. No fallback from Clef failure or uncertainty to Qwen is permitted. Directly requested Qwen work remains separate.
- `staged_wave_service.py` owns a durable workspace-scoped queue and one singleton service lease. It consumes one request inline, uses process-global stdout/stderr redirection, and keeps its render executor across requests. `max_wave_items` controls render prefetch sizing, not wave concurrency. The PowerShell wrapper clamps effective `MaxConcurrentStagedWaves` to 1. Do not implement overlap by threading requests through this service.
- Previous shared-overlap testing was 13% slower and lost OHP acceptance parity. Any future overlap work requires an isolated process design, exclusive GPU/resource ownership, and controlled same-input production-render/package checks. Parallel-wave execution is not currently implemented.
- Discovery, prefetch, downloads, and legacy item jobs are not all part of the staged-bake queue. The staged service is a vertical slice, not a generator-wide service. Preserve independent queue ownership, durable claims, ambiguous recovery, and existing service/lease boundaries unless a separately measured migration justifies a change.
