# Workout incumbent and controlled comparisons

A passing audit and semantic review establishes that a candidate is valid. Replacing a saved incumbent additionally requires improvement under the same approved objective order. The shared joint-candidate comparator owns that decision; the reviewer does not choose new numerical priorities.

## Selecting and retaining the incumbent

The normal CLI remembers the incumbent in the existing `conversation_meta.json`. Successful export seeds the first incumbent or advances it after comparison permits replacement. `/clear`, conversation switches and resume retain the reference. Retained conversations and exports are never rewritten to implement this selection.

For an existing verified plan, select its saved conversation explicitly:

```powershell
python workout_generator.py --incumbent-conversation build/workout_quality_approved_snapshot_20261103/workouts/conversation_sessions/30176ec9-88b0-4327-944e-dd9ded318fbc/messages.json --history-backup-file build/backup_conversion/workout_store_backup_2026-10-15_current_library_snapshot_evidence.json --require-load-calibration --no-reasoner
```

The reference contains its message-file path, existing draft ID and a SHA-256 fingerprint of the exact passing receipt. Appending later conversation turns does not select a different receipt. A missing or modified receipt stops comparison rather than silently removing the incumbent. This internal reference is excluded from model messages.

Normal preparation may offer definitions selected in a matching incumbent. Qualification may reuse only missing exact-context contracts from that pinned source: authority and input hashes must match, roles must agree with every finalized occurrence, and contradictory receipts or active definition feedback prevent reuse. Current contracts retain ownership. This carries semantic qualification evidence, never old loads or plan approval; an existing conflicting candidate remains unresolved.

There is one active incumbent per output directory. A test harness using a separate directory must explicitly select the same reference; it must not silently start without a baseline. There is no automatic scan of `build/` to guess which plan is best.

## Comparison and export

1. Verify each artifact's resolved decisions against its independently approved conversation ledger, including before a different-requirements scope exemption. A stale or inconsistent candidate remains blocked. Verify matching approved requirements, qualitative user sources, restrictions, library, history and calibration policy. Presentation changes do not change a requirement; quantities and priority order do. A genuinely different approved requirement set starts a different comparison scope. If reusable approved policy choices differ, classify the comparison as `inapplicable/different_approved_decisions` after the other authority checks pass. Candidate-specific concern acceptances, receipt explanations and absent/null bookkeeping do not establish a different policy scope; they still enter the normal objective comparison. Full-ledger consistency is checked before this distinction. This allows the current reviewed candidate to continue under its own approved scope; it makes no claim of improvement over the incumbent and computes no cross-scope objective comparison. Definition and qualification reuse still require matching authority, including decisions.
2. Apply the current shared ordering policy to an in-memory copy of the incumbent and rerun its native audit. Keep its original artifact untouched. If revalidation fails or authority differs, retain both candidates and stop for a decision.
3. Compare the exact audited plans with the existing joint objective formulas. Stop at the first differing approved objective. Lower-ranked savings cannot compensate for an earlier regression. Numeric ties retain the incumbent; the exact canonical incumbent can still be reviewed/exported again.
4. Apply this after semantic review for fresh drafts and repairs. Recheck at the shared export-review guard, including direct pipeline use. An unsuccessful comparison removes export approval and preview, records the comparison, and asks whether to retain the incumbent or investigate a controlled alternative. It does not start another repair automatically.
5. Update the incumbent only after successful export. A historical review is evidence for its original role assignments, not a new semantic approval of reordered work. Conflicting role evidence makes the comparison unresolved. Every proposed export still needs a current independent review and explicit export confirmation.

This changes no training requirement, credit formula, optimizer objective, contract version or model-output schema. It does not implement an automatic override for an inferior candidate. Deliberately choosing a different incumbent is an explicit operator decision.

## Controlled work before another paid run

Use the same approved requirements and reference throughout a comparison. Change one concern at a time: ordering on the incumbent menu, then selection, then grouping. Compare repairs against the incumbent too. Preserve the candidates and code-computed results, not just the winning summary.

The retained replay is `build/workout_incumbent_acceptance_20261103/replay.py`:

- It reproduces rejection of the newer 100-set export. Duration balance ties; movement-balance cost is 0 for the incumbent versus 2 for the newer export. The comparison stops there.
- It prepares `ordering_only_draft.json` and its current native audit: 102 sets and estimated times 80:21 / 80:21 / 80:15, with exact exercise prescriptions preserved.
- That ordering-only candidate remains unapproved for export until a current semantic review passes. Native acceptance never substitutes for that review.
- It checks retained source hashes and uses zero provider calls.

Another paid call should answer a named unresolved question from the current evidence. The ordering-only replay above used its recorded library snapshot. Changes to reviewed family metadata change the library fingerprint and require the normal restriction preflight and qualification before a new current review; historical approval must not be transferred to the changed library context.

The zero-provider replay in `build/workout_decision_scope_fix_20261104/replay.py` isolates the retained fresh-run blocker: the incumbent has no resolved decisions while the candidate has six independently approved decisions. It records the original authority failure, the new inapplicable scope, and current native/semantic gate checks without changing retained messages or creating an export. Scope separation cannot waive a stale decision receipt, source/restriction mismatch, changed library/history/calibration policy, native failure, semantic review or explicit export confirmation.

The comparator protects the approved measurable preferences between these candidates. It does not prove whole-library optimality, measured session time, personal fatigue or complete physiological suitability.

Supplying a reviewed weekly-dose reference does not freeze supersets. The shared solver may enumerate compatible pairings and compare keep/split arrangements under the same approved priorities. Explicit source-selection preservation and targeted redistribution retain their existing restrictions. The final arrangement still needs native validation, current semantic review and incumbent comparison before export.
